The workload was a label, not a variable

With the instrument finally calibrated, the next question was what sampling rate each kind of workload deserves. The first ninety-cell run came back perfectly clean — and completely empty.

The one idea to hold onto

A pipeline can execute flawlessly, pass every health check, and produce a beautifully structured dataset of nothing at all. Passing is not the same as measuring.

1
The oversight

Ninety clean cells with no workload in them

The design was a grid: five sampling rates × three durations × two workloads × three repeats. Ninety cells. It ran overnight, every cell completed, every operational check passed. Then someone looked at what was in them.

experiment_audit.md · Day 7 · 2026-05-22

"The cell.workload field is metadata only — it labels the row in the manifest. The orchestrator never SSHes to the VM to launch the workload binary. So the 90 cells contain idle Kali snapshots, not workload memory behavior. The 'workload' label is currently vacuous."

The grid varied five things correctly. The one thing the experiment was about was written down but never done.

The engineer's summary is the line worth keeping: "We built the matrix correctly but forgot the workload was a variable, not just a label."

What was done with them

The ninety cells were not thrown away. They were relabelled as what they honestly were — a characterisation of the capture pipeline itself, run ninety times under five different sampling rates. That is "the very thing it succeeded at", and the reproducibility numbers from it are cited for weeks afterward.

2
The double-bind

The same afternoon, a second wall

Hours later, with the missing count back-filled, a second problem surfaced. The analysis needs a minimum number of windows per cell to say anything. At the canonical settings, zero of ninety cells reached it. The best cell in the grid produced one window.

The arithmetic is brutal: reaching the target needs at least 3,328 snapshots. At the fastest sampling rate that is about seven minutes of guest time. At the slowest it is 1.87 hours per cell — for a grid of ninety.

In plain terms

Two separate requirements had been assumed to be one. "Enough windows for the statistics to be stable" and "enough samples for the frequency analysis to have resolution" are different constraints that happen to be written with the same number. Satisfying the second was never budgeted for.

The resolution was to record the count on every cell and not gate on it — window adequacy became the next experiment's question rather than this one's pass criterion. That single decision is why this particular check stays informational for the rest of the project, a detail that matters again in Entry 8.

The argument that changed how thresholds get set

The plan had said "accept if the score clears 0.8." Someone went and ran the scorer on deliberate nonsense — uniform noise, an off-frequency sine, all-zero memory — and it returned 0.41, 0.55, 0.62. So 0.8 was not "noise plus a margin." It was noise plus about 0.2, and nobody knew that.

The objection was that 0.8 is a convention from the segmentation literature and doesn't need re-deriving. The counter is the sentence that won:

"If the noise floor is 0.7, that's the headline finding. We'd be writing 'workload pair X separates at F1=0.78' and a reviewer asks 'is 0.78 above noise?' and we don't know. Cheap to find out."

Designed, and never actually run

A null-baseline probe was specified in detail — idle guest, 250 ms, 5 minutes, three replicates — and made a prerequisite for the pilot. But the numbers that appear beside it in the audit are labelled "simulated for this audit — would be replaced by real run output in production." The worked example is a placeholder, not a measurement.

So what this entry establishes is the principle: set the bar from measured noise, not from convention. The first time that principle was genuinely executed was much later, in the audit of Entry 8 — and when it ran for real, it did exactly what the objection predicted. It retired a gate instead of confirming one.

3
Adversarial trust

A health check that could not answer its own question

Overnight runs kept dying on a locking error: the virtualisation layer refusing a command because another operation held a state-change lock. The first fix polled the machine's reported state until it looked stable, then proceeded. The bug came straight back with a different lock holder.

experiment_audit.md · Day 8 · decision D-34

"domstate is read-only and does not acquire the state-change lock… My settle saw 'paused' twice in a row (stable!) and exited. Settle was checking the wrong signal."

The replacement is not a better poll. The settle step became an actual attempt to resume the machine, retried with backoff — because only a successful write proves the write lock is free.

Takeaway

The principle written down that day: don't trust read-only probes when the question is about write availability. Asking "does it look free?" and asking "can I actually have it?" are different questions, and only one of them is the one you need.

Three other defects surfaced in the same session, and one of them is the same species as the ninety empty cells. A cell reported ok (snapshots=8) where 444 were expected — off by fifty-five times, and still marked as a pass, because "ok" had been defined as snapshots greater than zero and no backpressure. It was replaced with a quantitative bar: the ratio of snapshots actually taken to snapshots expected.

Be honest about the limits

Two of the four bugs that day were not code at all. One was a placeholder from the operator's manual pasted into a live command verbatim, so the machine dutifully tried to execute a path with angle brackets in it. Another was an interactive password prompt appearing in an unattended overnight run. Neither is glamorous; both cost a night.

4
The order of operations

Measuring before building

To measure the quality metrics at all, the raw memory images have to be kept. Keeping them was arithmetically impossible: a single long cell would produce around 445 GB, and the ninety-cell grid would need "many terabytes".

The obvious move is compression, and the obvious next move is to start writing a compression layer. What actually happened was a decision to run the benchmark first and write no code until it returned. On one real gigabyte-sized memory image:

MethodCompressed toTime
zstd level 315.12%3.1 s
zstd level 914.22%13.0 s
zstd level 1912.33%318.8 s
gzip level 316.60%10.9 s

The engineer's reaction is in the log: "15% is way better than my 30% prior." The highest setting buys 2.8 percentage points for a hundredfold slowdown, so the level was fixed at 3 and deliberately not exposed as a tunable option.

Where this earns its keep

And then the honest conclusion: even at 15%, the full archive is about 6 TB — still forty times over budget. So retention stayed off by default. The benchmark did not justify the feature; it correctly killed it for now. Entry 10 is where this problem gets solved properly, by a method that does not compress snapshots individually at all.

The alternative that shipped instead was to compute the measurement during capture and delete each image as soon as its successor arrives — two images alive at any moment, a fixed ceiling of about 2 GB regardless of how long the run goes. Making that asynchronous mattered more than it sounds: the synchronous version added a second per snapshot, which "kills the 100 ms regime — the very regime where detection matters most."

5
The surprise

Sampling faster made the answer worse

With the data layer working, the ninety-cell grid ran for real. The headline is that the two workload types separate enormously: the bursty one varies about 76 times more than the steady one at the median. The phasic-versus-steady distinction is not an assumption of the taxonomy — it is visible in the raw variability.

The unexpected result is what happened across sampling rates. The fastest setting was worse at detecting the bursty workload's phase boundaries than a slower one — and not because it collected fewer samples. Restricted to cells with plenty of snapshots either way, the fast setting still never achieved a perfect score, while the slower setting had no total failures at all.

Why

Two mechanisms, both recorded at the time. The encryption-start transient occupies several consecutive fast windows, so the signal stays high and flat with no single step carrying the jump a boundary detector keys on. And when the trajectory is spiky, the peak drifts four to seven positions away from where the truth marker says it should be.

Takeaway

Framed carefully in the write-up as temporal-resolution mismatch, not aliasing — and as an argument against the naive assumption that a finer sampling interval always means better resolution. Sometimes it just spreads the event you were trying to catch across more frames until none of them contains it.

The design-justified recommendation table was replaced with a data-driven one. And one more line was filed, almost in passing, that becomes the central problem of Entry 8: four cells with plenty of snapshots and a zero detection score, "likely indicating ground-truth phase markers misaligned with VM snapshot timestamps."

6
The failure mode that keeps returning

Failing for having succeeded quietly

One cell in the sub-pilot produced 28 clean measurement pairs and perfectly good numbers. It was marked as a failure. The chain took three hops:

  1. One slow call to the virtualisation layer timed out.
  2. The timeout escaped to an outer handler, which wrote a warning line instead of the canonical status line.
  3. The validator's pattern found no match, returned nothing, and "nothing" was treated as a failed check.

The cell failed its gate because nothing had gone wrong loudly enough to be reported in the expected format.

How to test

The fix has two halves, and the second is the important one: catch the timeout inside the loop so the canonical line is always emitted, and make the validator treat a genuinely missing line as "not applicable" rather than as "failed". A check that cannot distinguish "this went badly" from "I could not tell" will eventually report the wrong one.

The same shape appeared twice more in this period. A gate failed all six cells of a sub-pilot because its expected-snapshot formula had been calibrated before the new data layer halved the available disk bandwidth — the data was sound, only the gate misfired. And when the full run finally completed, transient disk use peaked at 59.5 GB against a 5 GB design target, a twelvefold overshoot caused not by any single cell but by cleanup running in blocks rather than per cell.

Be honest about the limits

Every threshold recalibrated in this entry was moved after seeing where the data landed. Each move is individually defensible and individually documented. Cumulatively it is a pattern the project keeps having to argue with — and in Entry 7 it gets argued with explicitly.

Glossary

Hover any dotted term for its definition.

Cell
One box in the experiment grid — a single combination of sampling rate, duration, workload and repeat. The unit that either passes or fails.
Analysis window
A run of consecutive snapshots analysed together. Frequency analysis needs a minimum number of them, which is the constraint that bites in this entry.
Backpressure
What happens when snapshots arrive faster than they can be processed. The queue fills and the producer is forced to slow down.
