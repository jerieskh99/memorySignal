## 2. Must change before build

2.1 The roll-up of grid-independent per-kernel refusals (SPEC 3.5.7, 812 to 817; 3.5.1, 756 to 757; 3.5.2, 762 to 763). Two per-kernel verdicts do not depend on (W, H): `TREND_PRESENT` is computed from the whole series (SPEC 754 to 756), and `G2_ABOVE_NYQUIST` is a property of T against dt (SPEC 763). Both are in `is_refusal`. Under `grid_rollup = "all_kernels"` a gate "passes at a grid point when it passes for every kernel ... for which the gate is applicable"; the SPEC does not say whether these two verdicts make the kernel "not applicable" or "not passing". If they count as not passing, one trending kernel blocks G1 at every integer W, and nbody, the only kernel with a declared pass period on this dataset, at T_pairs about 0.15 (SPEC 690 to 691), blocks G2 at every W on every rung. Which of the two happens is decided by a reading the builder makes; that is the dependence my 1.5 condition forbids. The definitions call both verdicts refusals of a claim about the kernel, not of the grid point: CR 2.1 item 3 says a trend "hands the cell to the whole-cell reading rather than discarding it"; item 4 says above-Nyquist is "a refusal of the rhythm claim, never a pass".
Correction: add to 3.5.7 the parameter `rollup_kernel_refusals = "not_applicable"` (alternative `"blocks"`) with this sentence: "For the roll-up at an integer-W point, a kernel whose G1 is `TREND_PRESENT` is not applicable for G1, and a kernel whose G2 at a given dt is `G2_ABOVE_NYQUIST` is not applicable for G2 at that dt (the roll-up is computed per dt column, then combined by the rule of 3.5.2); the verdict stays in the kernel's own row of `table5_long.csv`; `table5_grid.csv` gains `n_kernels_na_G1` and `n_kernels_na_G2`; the trending kernel's whole-cell reading is its `Wall_Hall` row, which exists for every cell." State that the `idle` row is excluded from the roll-up (it is the control, not an encoding target), and define `gates_passed` as "k of m" over applicable gates so the best-feasible fallback is also determined. Record the parameter in section 8 and in `selection.json` `params`. Add: the split stage never routes cells by a G1 verdict (this keeps condition 4).

## 3. For the author

1. Item 2.1 is the decision that matters most on this dataset. With nbody declared and above Nyquist, and any one kernel trending over 600 s (rmat_gen, bnb_tsp and the lexer are the candidates from Table 3), the treatment of these two verdicts decides whether any (W, H) can ever pass acceptance. My recommended default is `not_applicable`, on the definitions' own words; `blocks` is defensible only if you want the paper to report that no point passed. Either way it lives in `params`, not in a builder's head.
2. G-F part (i) as specified (SPEC 641 to 647; 8.15) is a within-trace, window-level test with a window-level shuffle. It departs from CR 2.1 item 9's "a window-level shuffle is not to be used" of necessity, since there is one cell per rep label. B1 found within-trace to be the ceiling split: adjacent windows of one cell resemble each other through slow host drift, so eight idle reps may separate within-trace even when they share one distribution, and `GF_VOID` would then void every rung for the wrong reason. Decide whether `GF_VOID` from this executable form voids the rung (the SPEC's bite) or is reported as "separable within-trace at the window level" with the void reserved for a unit-level test you declare later. I recommend exposing `part1_consequence = "void" | "report"` and choosing before the data.
3. C6 as re-mapped no longer fails on a `seq` gap (SPEC 587; `validate_campaign.py` line 16 makes a gap a hard failure for `apf_queue`). The re-map is right for sparse mode (section 1), but it is a change to a pre-registered gate and should be recorded as such, as ML asked for the B1 restatements (P2 Sec. V 5.1).
4. The pass table's `inferred:` rows (SPEC 665 to 669) must come from source and base parameters (VME 1.5), never from the trajectory, the cepstrum or any toolkit output; otherwise G2, and through it (W, H), reads an interpretation of the data it is fixed on. Put that sentence in the template's header comment and in the runbook.
5. `--assume-failed-zero --assume-reason "AA A5 ..."` is the runbook's default path (SPEC 1337). A5 itself says the orchestrator's re-run path at `fcc184e` is to be verified in the writing epoch. Until then the zero is a declared assumption carried in every persistence reading's `params`; that is correct, and it should be said once in Limitations.
6. Building the feature matrices at all thirteen points (2.2) is cheap and makes the split stage re-runnable at any point by anyone auditing the selection, which is the practical content of "computed and kept".
7. `head_drop.csv` is keyed by kernel (SPEC 491). It is a Stimulus fact from source, so it does not carry the label into the features, but it changes `K_median_cell` and the window count for that kernel's cells. If you set a non-zero value, record its source (the phase marker in the kernel's source, by file and line) in the `reason` column so it is auditable as source-side, not signal-side.
