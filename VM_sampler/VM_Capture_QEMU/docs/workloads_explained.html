Part 1

The big picture

There are two machines involved. The host is the real server. Inside it, one small virtual machine — the guest — is the actual subject being studied. Everything the guest does happens inside that 964 MB of pretend RAM, walled off from the host.

A step (also called a test or a cell) is: boot the guest, run one workload inside it for about 60 seconds, take a snapshot of its memory every half-second, then shut the guest down and move to the next step. A campaign is all 101 steps run in sequence — currently around 9-10 hours end to end.

Why 101 different workloads instead of one? Because the thesis question is "can we tell what a program is doing just by watching which memory pages change?" — and that question can only be answered by giving the detector a wide variety of real behaviors to tell apart. One workload proves nothing; a hundred different shapes of behavior is what makes the signal meaningful.

Nothing in this page requires you to remember the mechanics of compression or storage — that's covered in a separate page. This one is only about the workloads themselves: what they do, and why some of them broke.
Part 2

The nine families

Every workload belongs to a family, and the family name is literally the first word of its filename (cpu_hash_loop_v2, mem_writemag_sweep_v2, and so on). Think of a family as a chapter in the textbook — each one exists to teach the detector a different category of behavior.

cpu 3

Pure computation — hashing, matrix multiply, branch prediction stress. Deliberately writes almost nothing to memory. This is the "quiet baseline": what does no real memory signal look like?

cache 3

Access patterns aimed at CPU cache behavior — a hot loop that stays in cache, a cold scan that sweeps far past it. Some are near-silent, some are loud; the family exists to test that boundary.

mem 7

Deliberately dirties large regions of memory in different patterns — sweeping, random writes, page faults, file mapping. This is the family most central to the thesis: the "loud" end of the spectrum.

thread 3

Concurrency stress — lock contention, producer/consumer queues, parallel allocation. Small memory footprint; tests threading overhead, not memory volume.

io 2

Disk-facing behavior — reading a cache-hot file, writing directly to disk. Meant to look different from pure-memory workloads, which is exactly what the tmpfs contamination broke.

mixed 3

Deliberate combinations — CPU+memory, memory+I/O, CPU+I/O. Tests whether combined behavior looks like the sum of its parts, or something new.

app 6

Realistic application-shaped work — gzip compress/decompress, JSON parsing, SQLite queries. Meant to resemble real software rather than a synthetic microbenchmark.

sandbox 8

Ransomware-behavior simulations (sequential, batched, selective, slow-burn file rewriting) plus "stealth" variants that write slowly and small, trying to blend in. The security-detection angle of the thesis.

kernel 64

By far the largest family — the Berkeley "dwarf" compute kernels: linear algebra, graph algorithms, spectral methods, particle simulations, dynamic programming, and more. Exists to sample a huge diversity of real scientific-computing memory-access patterns. (Plus 2 mp_* methodology scripts that analyze other steps' results rather than running their own workload.)

The kernel family is worth pausing on. At 64 of 101 steps, it is most of the campaign, and it is the least uniform — a graph traversal and a spectral transform have almost nothing in common except that both are "kernel" workloads. That is why kernel workloads produced most of the recent failures: 64 different C programs, each sizing its own memory in its own way, is simply more surface area for a sizing bug to hide in than the other eight families combined.
Part 3

Why tests fail — four root causes

Every failure across the last several rounds of testing reduces to one of these four. None of them is about a workload's logic being wrong — every failure so far has been about fit: the workload asking for more of something than the guest actually has.

1. Memory bigger than the guest

The guest has 964 MB of RAM. When a workload asks the operating system for a block of memory — a call named mmap — and asks for more than the guest can give, the request itself fails outright. The workload doesn't run slowly or partially; it gets a flat refusal and exits immediately with an error like mmap(2147483648) failed: Cannot allocate memory.

Not all memory is equally dangerous here, though. Memory backed only by RAM — called anonymous memory — is the risky kind, because the guest cannot get it back once given out. Memory that mirrors a file on disk — file-backed memory — is much safer: the guest can always throw those pages away and reload them later, a property called being evictable. This distinction is exactly what separated a real bug from a false alarm later in this document.

2. Scratch on the wrong disk

Workloads that write files need somewhere to put them — a scratch directory. The guest's default location for this, /tmp, looked like an ordinary folder but was actually tmpfs — a fake disk that lives entirely in RAM, sized at roughly half the guest's total memory by default. Two consequences followed from that one fact: first, anything larger than ~480 MB simply couldn't be written; second — and more subtly — writing a file there was indistinguishable from writing to memory, because it was memory. An "I/O" workload writing to tmpfs wasn't doing disk I/O at all — it was doing a memory write wearing an I/O costume, which quietly invalidated exactly the comparison those workloads exist to make.

3. Unbounded defaults

Many workloads accept a safety-budget flag, --max-mb, which defaults to 8192 MB when nothing else is specified. That default was written for a full-sized machine, not a 964 MB guest — and 69 of the 101 workloads accept it, with none of the 101 campaign steps setting it explicitly. For most of them the default never mattered, because they only use it as a ceiling check. For six of them, though, it was used to directly size a memory block — so those six tried to reserve the entire 8 GB default before doing anything else, and failed immediately.

4. Leftover mess from previous runs

Some workloads write real payload files and never delete them when they finish — this was true by design for the whole sandbox family, since none of them clean up their own output. Left unmanaged across 101 sequential steps, those files would eventually fill the guest's disk regardless of any single step's own size. The fix for this lives on the host side (a reclaim step after every cell), not inside the workloads themselves.

Part 5

Where things stand now

All nine issues above are closed. The automated preflight check — which runs all 101 workloads briefly before committing to a full 9-hour campaign — currently reports everything ready. That check itself went through its own round of fixes this session (a loop that was silently only testing 1 of 101 workloads, a memory reading that measured the wrong process), which is a separate story from the workload fixes above: those were bugs in the checker, not in any test.

The practical takeaway: the next full campaign run should proceed without hitting any of the nine problems above, because each one is now either fixed in the workload's own configuration or correctly judged by the check that evaluates it.

Glossary — full list

Every term below also appears inline above with the same definition on hover.

TermDefinition
hostThe real physical server that runs the guest VM and does the capture, compression, and storage work.
guestThe virtual machine under test, with its own 964 MB of RAM separate from the host.
workloadOne small program that performs one specific behavior, so its memory signal can be observed in isolation.
step / test / cellOne run of one workload with capture running around it — one numbered entry in the campaign.
campaignThe full run of all 101 steps back to back, unattended.
snapshotA full 1 GB copy of the guest's memory, taken roughly every 500 ms while a workload runs.
mmapA system call a program uses to ask the OS for a block of memory, or to map a file into memory.
anonymous memoryMemory backed only by RAM/swap, not by a file — cannot be reclaimed by writing it elsewhere if the guest runs low.
file-backed memoryMemory that mirrors a file on disk; can safely be dropped and reloaded later.
evictableMemory the OS can safely discard under pressure and reload later without loss.
tmpfsA "disk" that actually lives in RAM — writing to it consumes memory, not real disk space.
scratch directoryA temporary folder a workload writes its working files into during a run.
--max-mbA safety-budget flag many workloads accept, capping their memory use; defaults to 8192 MB if never set.
preflight / QAAutomatic checks run before a real campaign, to catch a broken workload in minutes rather than hours.
methodology (mp_*)A script that analyzes another step's results rather than running a workload of its own.
