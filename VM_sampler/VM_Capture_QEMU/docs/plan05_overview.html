Plan 05 · capture-side throughput pilot

Faster snapshots,
same signal.

Every few seconds we pause the virtual machine and copy its whole memory to a file. That copy is slow, and it is slow that decides how much data each experiment can collect. Plan 05 makes the copy cheaper so we collect more, while proving the cheaper copy still measures the same thing. We do not change the analyzer at all.

One-paragraph version. Copying the VM's memory takes most of each snapshot's time, so a short experiment only yields a few snapshots, and our analysis needs more than a few to be reliable. Plan 05 speeds up the copy three ways (smaller guest RAM, writing to a RAM-disk instead of an SSD, deleting old copies as we go), and gates every change behind three pass/fail checks: is it at least 2× faster, does it still record the same memory signal, and does it stay under a disk budget. The live pilot (Wave 2) is now done. Its headline gate “failed” — but investigating why turned the result inside out: the real bottleneck was never the copy itself, it was keeping old copies on disk. Deleting them as we go already cut the copy from 7.06 s to 0.79 s and raised snapshots from 14 to 79 per 120 s. See The 7-second mystery. Waves 3–4 then fixed the analysis gate, confirmed the cause, and built that faster capture into the real pipeline as a selectable APF mode (a Rust apf_calc consumer) plus a sustain-loop so workloads churn the whole window — only the full data campaign is left.
01

The problem

The snapshot is slow because of one step: copying RAM.

A single snapshot does several things (pause the VM, copy its memory, resume it), but one step dominates everything else — writing a full copy of guest memory to disk. Because that one step is so slow, a fixed-length experiment fits only a handful of snapshots, and the downstream analysis is left with too few data points to trust.

In plain words

The memory copy eats roughly 4 out of every 5 seconds of a snapshot. So a short run produces a short, choppy data series. Our analyzer chops that series into overlapping windows and studies them — but with so few snapshots, most windows are missing, and the statistics built on them get shaky.

The measured numbers

The RAM copy (pmemsave) is a median 7.06 s of the 9.75 s snapshot cycle — about 81% (range 2–24 s). At the frozen analyzer setting (W,H)=(8,4), 53 of 132 cells end up with ≤3 analysis windows.

The signal we care about is called APF (Active Page Fraction): of all the memory pages, what fraction changed since the last snapshot. It is our measure of how “alive” memory is over time. A faster snapshot is only useful if APF still looks the same — that is what the fidelity check defends.
Update after the pilot (Wave 2): the 7.06 s was not the copy's true cost — it was inflated by keeping old dumps on disk. The original campaign never deleted them (keep_dumps=true on 125/128 cells), so the live folder filled during each run and every write slowed. Delete each dump the moment it is used and the same copy costs only ~0.79 s — same machine, same RAM. The full detective story is in The 7-second mystery.
02

The fix

Make the copy cheaper → more snapshots → more data.

If the memory copy is cheaper, more snapshots fit in the same wall-clock time. More snapshots means a longer data series, which means more analysis windows of the same size — and the shaky statistics get solid ground again. We have three independent ways to make the copy cheaper:

LeverWhat it doesRisk
guest RAM Give the VM less memory (1024 → 512 → 256 MiB), so there is simply less to copy each time. High. Needs a VM resize and a cold reboot, and the memory-heavy workloads run out of RAM below 1024 MiB.
dump target Write the copy to a RAM-disk (tmpfs) instead of an SSD — memory is faster than disk. Low. Just a config path.
delete-as-you-go Remove each old copy right after it has been used, so the disk never fills up with a backlog of dumps. Low, but it was tangled up with another setting; Plan 05 untangles it (see the matrix note).

The RAM lever is the risky one (reboots, out-of-memory crashes), so we set it aside as a separate side-experiment that never blocks the main pilot. The pilot itself drives the two safe levers: where the copy is written, and when old copies are deleted.

The bar for success: a lever must make the copy at least 2× faster, without changing the APF signal, and without blowing a disk budget. Those three are spelled out next.
03

The three checks

Each candidate setting (a “lever arm”) is compared against the current baseline — SSD, keep-the-dumps — and is accepted only if it passes all three checks. Because each check tests one separate thing, a failure tells you exactly what went wrong.

G-T1
faster?
Is the copy at least 2× faster? The new setting's typical copy time must be at most half the baseline's. This is the whole point of the pilot — if it is not faster, none of the rest matters.
G-T2
same signal?
Does APF still look the same? We compare the APF values from the two settings three ways, and all three must agree that nothing meaningfully changed: the averages match (within a small margin), the spread matches, and the overall shape of the distribution is not detectably different. We use an equivalence test, not an ordinary difference test — the difference between “we found no change” and “we confirmed it is the same” matters here, and only the second one is good enough to trust a cheaper snapshot.
G-T3
fits on disk?
Does it stay under the disk budget? While the run is live, a small background watcher records the largest the dump folder ever gets. That peak must stay at or below 3 GiB.
Why an equivalence test (and not just a t-test). An ordinary test failing to find a difference is not proof there is none — it could just be weak data. The equivalence test flips the burden: it only passes when the data positively shows the two settings land inside a small “close enough” margin. So “fidelity preserved” has to be earned, not assumed.
04

What we actually test

3 workloads × 2 durations × 4 settings × 3 repeats = 72 runs.

The variations
  • 3 workloads — one steady and busy, one rhythmic with the strongest periodic signal, and one that uses ~1 GiB of memory (the stress case for the RAM lever).
  • 2 lengths — a short 120 s run and a long 600 s run.
  • 4 settings — write to SSD or RAM-disk, crossed with keep-the-dumps or delete-as-you-go.
  • 3 repeats of each, for stable numbers.
The four settings (arms)
  • ssd_keep — today's setup, the baseline everything is compared against.
  • ssd_selfclean
  • tmpfs_keep
  • tmpfs_selfclean

All four record the APF signal. The big speed difference was expected to come from SSD → RAM-disk — but the pilot measured only 1.35× (the dump is already cheap at 1 GiB; see Results).

The tangle we had to undo. In the production tool, one switch (“keep the dumps?”) secretly controlled two things at once: whether dumps were kept, and whether the APF signal was even recorded. Turning dumps off also turned the signal off. The pilot needs the APF signal on every setting, so we added an opt-in switch that records APF no matter what. It is off by default, so if you do not ask for it, the tool behaves exactly as it did before.
05

Who runs what

The work splits cleanly in two, on purpose, so the risky live machine never holds up the safe desk work.

Laptop (offline)

All the code and analysis: the fidelity check, the results aggregator, the driver changes, the runner that loops everything, the tests, and this page. No live VM. This is everything Wave 1 delivered.

Server (live)

All the real captures against the VM: the risky RAM-resize probe, the pilot run, the follow-up runs on more workloads, and the final campaign. The server runs plan05_run.py.

06

What's built (Wave 1)

All written on the laptop, all unit-tested, none of it touches the analyzer.

plan05_fidelity.py
The “same signal?” check (G-T2): compares two APF series by average, spread, and shape, and returns pass/fail.
plan05_aggregate.py
Takes all the runs, applies the three checks to each setting, and writes a summary plus a recommendation of the best setting that passes everything.
run_timing_…experiment.py
The single-run driver, now with off-by-default switches: record APF (--stream-apf), watch peak disk (--instrument-peak-disk), write to a RAM-disk (--image-dir), and a safety check that refuses to run if the configured RAM size does not match the real VM.
plan05_run.py
The runner that loops the driver across all 72 runs, starts the VM once, does the safety check once, and gathers the results.
tests/
Five test files, 58 checks in total — including a proof that with none of the new switches on, the tool behaves byte-for-byte like before, a check on the opt-in sudo-delete that keeps the keep-dumps arm under its disk budget, and the recalibrated effect-size KS fidelity check.
Nothing changes unless you ask. Every new capability is behind a switch that defaults to off. With no switches, the old behavior is preserved exactly — and that is one of the tested guarantees, not just a claim.
07

How to run it (on the server)

The guest workload commands are specific to the server, so you pass them in by hand (the runner refuses obvious placeholder text):

python3 plan05_run.py \ --workload-command app_hashtable_intensive_v2='/usr/local/bin/app_hashtable_intensive --rounds 8' \ --workload-command sandbox_scanner_metadata='/usr/local/bin/sandbox_scanner_metadata' \ --workload-command mem_workingset_sweep_v2='/usr/local/bin/mem_workingset_sweep' \ --ssh-target kali@192.168.122.42 \ --tmpfs-dir /dev/shm/plan05_dump \ --aggregate

Each run writes its own result file; the runner gathers them into one, and --aggregate produces plan05_summary.json with the three checks for every setting and a recommended winner. To preview the exact commands without touching the VM, add --dry-run (safe to run on the laptop).

Reading the result: start at the recommendation — it names the winning setting. Then each setting's three blocks tell you whether it earned the speed-up, kept the signal, and stayed under the disk budget.

Results (Wave 2)

72/72 runs completed. On paper, no arm cleared all three checks — but the “failure” turned out to be the win in disguise (see The 7-second mystery).

The full matrix ran on the server (a mid-run reboot cost six cells, since resumed). Every cell produced timing, an APF trajectory, and a peak-disk reading. Here is how the three checks landed.

faster?

But the gate compares each arm to that baseline — and the baseline already deletes dumps as it goes (every arm streamed APF). So all four arms sat at the same fast floor and the gate saw no gap. The honest comparison is this floor versus the old keep-everything campaign — a ~9× cheaper copy. See The 7-second mystery.
G-T3

Passed everywhere — the disk fix held. Peak live-dump stayed 2.3–3.0 GiB, under the 3 GiB cap, across the whole run. The keep-dumps arm — which would otherwise pile 40+ GiB on a folder it has no permission to delete from — was kept bounded by an opt-in sudo-delete fallback added this wave.
G-T2
same signal?
Mostly fine; the failures are now well understood. After recalibrating the gate (Wave 3), 9 of 18 lever comparisons pass. The recalibration: the old gate rejected on the KS p-value, which at ~1,400 samples flags differences of 0.0001–0.002 APF — far below the 0.02 we care about. It now judges the KS statistic (the actual distribution gap), so negligible differences stop being false failures. The deeper finding from the audit: APF is near-zero in nearly all 72 cells (both durations) — the guest barely changed pages — so most “passes” are matching near-idle signals, and the few real failures are replicates where the workload actually churned (e.g. mem_workingset@600s = 0 for some reps, 0.25 for others). This is not a delete race (zero APF=0 entries). The Wave 3 probe found the cause: app_hashtable and sandbox_scanner treat --duration as a cap and finish in 1–2 s, so the guest idles the rest of the window; mem_workingset honors the duration and churns. Fix: sustain the workloads (loop-wrap) for the capture window.

09

The 7-second mystery

The gate said “fail.” Asking why turned the result inside out.

What we believed going in

The papers measured the memory copy at a median 7.06 s — 81% of a 9.75 s snapshot cycle. That slow copy was the assumed villain: it let a run fit only a handful of snapshots, so APF trajectories were short and the analyzer was starved (53 of 132 cells had ≤3 windows). Plan 05's bet was that a cheaper copy — via a RAM-disk or a smaller guest — would buy more snapshots.

What the pilot showed

72 runs. The baseline copy came out at 0.79 s, not 7 s. tmpfs shaved it to 0.59 s — only 1.35×, not the required 2×. On its face: every arm tied, the throughput gate failed across the board, a null result.

The search: why 7 s before, 0.79 s now?

Rather than burn another seven-hour run, we stopped and investigated offline. Three suspects: (1) the old campaign used a bigger guest (copy time scales with RAM); (2) the old number was inflated by the full pipeline running at once (the consumer reading dumps back, competing for disk); (3) the disk is simply faster now. We pulled the original producer_stats figures (recorded in the round-2 reviewer memo) and compared regimes.

What we found

The old 7.06 s was never a constant — it was the median of a wide, right-skewed spread: 0.76 / 7.06 / 21.57 s (min / median / max). Our pilot's 0.79 s sits right on that distribution's minimum. And the decisive detail: the old campaign ran keep_dumps=true on 125 of 128 cells — it never deleted the dumps. They piled up on disk for the whole run.

The fingerprint. Two independent signatures confirm it. (1) The old copy time is right-skewed all the way to 21.57 s — what you expect when a cost grows during a run. (2) Old snapshot counts grow sub-linearly with time (14 / 26 / 53 for 120 / 300 / 600 s) — the cadence slowed as the run went. The pilot's counts grow linearly (79 → 398 for 120 → 600 s) — constant cadence, because it deletes as it goes.

The reason

The copy cost is not fixed by RAM alone — it is dragged up by a filling disk and a busy one. Keep every dump and the live folder grows snapshot by snapshot; the consumer reads that backlog; writes slow and contend. That is what stretched the median to 7 s and the tail to 21 s. Delete each dump the instant it has been used and the folder stays near-empty, so every copy runs at the device floor — 0.79 s on SSD, 0.59 s on tmpfs — no matter how long the run is. Same machine, same 1 GiB guest; the only thing that changed is retention.

Why the gate “failed”

The pilot ran every arm with --stream-apf, which deletes the previous dump right after it is differenced. That is delete-as-you-go — applied to all four arms, including the ssd_keep baseline. So the baseline already had the cure. G-T1 compares each arm against that baseline; with both sides already at the fast floor, it correctly saw ~1× and reported “fail.” The gate measured the wrong contrast. The honest contrast is the old keep-everything campaign versus delete-as-you-go.

Which earlier conclusions were wrong

  • “Null result / dead end” — wrong. The throughput goal was met, by ~5–8×.
  • “Guest RAM is the real lever” — wrong. Retention is. RAM was never the cause of the 7 s.
  • “tmpfs is the win” — overstated. tmpfs is a small extra (1.35×) on top; the deletion is the win (~9×).

The fix, and why it works

The fix is delete-as-you-go — stream the APF computation and remove each previous dump the moment it has been used — made reliable on the SSD baseline by this wave's opt-in sudo-delete fallback (the dump folder is owned by a different user, so the plain delete was silently failing; that is the same bug that would otherwise have piled 40+ GiB). It works because it keeps the live folder near-empty, so the copy never pays the accumulation-and-contention tax and stays at the device floor. Faster copies → more snapshots → longer trajectories → more windows → the degrees-of-freedom starvation that forced the papers' coverage and SNR hedges is relieved.

Next steps

  1. Measure the win as a clean contrast. Re-run a small matrix with a true keep-everything baseline (no streaming delete) versus delete-as-you-go, so the ~9× copy and ~6× snapshot gain land in one table instead of being inferred across campaigns.
  2. Or adopt it now. The 79-vs-14 evidence already stands; turning on delete-as-you-go in the production pipeline solves the trajectory-length problem the thesis flagged.
  3. Sustain the workloads — done (Wave 4). The probe found the near-idle cause: app_hashtable / sandbox_scanner treat --duration as a cap and exit in 1–2 s. The opt-in SUSTAIN_LOOP re-runs each workload until its --duration elapses; verified live (app_hashtable APF 0.0018 → 0.0875).
  4. Recalibrate the fidelity gate — done (Wave 3). The KS leg now judges the distribution gap (effect size) instead of the p-value, so large-sample runs stop false-failing; 9/18 lever comparisons pass.
9.7

The full campaign — 66 cells, the result we were chasing

The production pipeline (delete-as-you-go + sustain-loop + the Rust apf_queue consumer, with workload scratch on real disk) ran the complete v3 matrix: 11 workloads × {120, 300, 600} s × 2 replicates = 66 cells, at the locked cadence (intervalMsec 500, RAM 1024 MiB). All 66 finished cleanly.

The headline: 0 of 66 cells are degrees-of-freedom starved (≤3 analysis windows at the frozen (W,H)=(8,4)), against the v3 baseline of 53 of 132. The trajectory-length problem that forced the papers' G2/G3 hedges is gone. Across the 66 cells the pipeline produced 29,003 snapshot pairs and 7,159 analysis windows.

The workload battery — what each one is and why it is in the set

Eleven workloads spanning three families and the full memory-activity spectrum. The point of a battery this wide is to stress two things at once: the capture pipeline (does it hold up under heavy I/O, light load, long runs?) and the APF signal itself (does it separate a loud workload from a quiet one in a stable, reproducible way?).

Reproducibility is the validity proof

Across the 33 matched workload×duration pairs, the mean |rep1 − rep2| in APF is 0.0098, and the memory-microbench workloads repeat to the fourth decimal (mem_workingset 0.2509/0.2507/0.2505 in both replicates). A broken capture yields random noise, not numbers that reproduce across independent boots — so the signal is real and stable. The single large gap (0.189) is ransom_selective@600 s rep1, an under-sampled cell (39 pairs); its rep2 is healthy (88 pairs), and the two-replicate design is exactly what surfaces such variance.

Beyond the mean: burstiness, duty cycle, and trajectory shape

The 18 “IDLE?” flags are real low signal, not failures

The analyzer flags any cell with mean APF < 0.01. Eighteen cells trip it — and they are exactly three workloads, each consistent across all six of its cells:

WorkloadAPFWhy it is genuinely low
ransom_slowburn~0.0022 Drips one file every 3 s by design — little memory churn.
ransom_batched~0.0077 I/O-bound — moves bytes to disk rather than rewriting RAM.
mem_pagefault_density~0.0050 Generates faults, but page contents barely change.

All three repeat to 3–4 decimals across replicates — the signature of a real measurement, not an idle miss. The 0.01 threshold is simply miscalibrated for low-churn workloads. This is itself a research finding: two of the three are threats (low-and-slow and I/O-bound ransomware) that are nearly invisible in APF alone — a detector built only on APF would miss them, so APF should be paired with an I/O-rate signal.

Pipeline robustness during the run

  • SSH hardening earned its keep. Exactly one cold-boot rc=255 occurred; the consecutive-probe wait + single retry recovered it and the cell still finished rc=0.
  • Disk fix held. Zero “No space” events; delete-as-you-go kept host dumps bounded (the 933-snapshot cells alone would be ~900 GiB un-deleted). The ~72 GiB the host lost is one-time guest-image inflation (qcow2 high-water mark), reclaimable with fstrim + compact.
  • Every cell self-validated. The per-cell guest scratch wipe fired on all file-writing cells; no cross-cell accumulation.

What the validation surfaced — the ransom_batched memory cap. The orchestrator log held 2.17 million copies of one workload line, [ERROR] in-memory footprint exceeds --mem-cap-mb, and all of them come from ransom_batched (all six of its cells). Conclusions and thesis impact

  1. The capture-side problem is solved end-to-end. Delete-as-you-go + sustain-loop + the Rust consumer + scratch-on-disk turn the starved v3 capture (53/132 cells with ≤3 windows) into a fully-powered dataset (0/66). Downstream statistics now have the degrees of freedom the papers lacked.
  2. APF is a valid, reproducible discriminator. It spans 0.002–0.41 in the expected order and repeats across replicates to ~0.01 mean absolute difference.
  3. APF's blind spot is in the mean, and peak/variance shape features measurably narrow it (built + measured, see §9.8). Appending five shape features (max, p95, CoV, peak-to-median, duty-cycle) to the leakage-free AGNOSTIC set lifts the honest (leave-one-workload-out) threat/benign accuracy 0.636 → 0.788 and anomaly ROC-AUC 0.74 → 0.93 (LOF), recovering batched (0.17→1.0), scanner and seq. Two near-idle workloads stay irreducible — the low-and-slow slowburn (threat) and the bursty-low pagefault (benign): opposite labels, mutually confusable, needing a non-APF (I/O-rate) signal.
  4. Page granularity matters. A 64-byte write dirties a full 4 KiB page (writemag ~0.25), so APF reflects pages touched, not bytes changed — relevant when interpreting absolute APF levels.
  5. Continuous-write workloads stay thin at 120 s. ransom_selective and ransom_seq bottom out at 4–14 windows (sustained writes slow pmemsave); prefer their 300/600 s data. Bursty (batched) and pure-RAM workloads keep the full ~0.6 s cadence and are unaffected.
9.8

Downstream: behavioral identification + anomaly detection

With the capture fixed, we fed the 66-cell dataset through the existing analysis pipeline (an adapter into the cells-dir schema → plan03_sweep features → the classifiers). The question: how much of a workload's behavior survives in the single APF scalar — can we identify the workload, its behavioral family, or flag an unseen one as anomalous? Framed as behavioral characterization, not a security detector (the phasic class is synthetic write-rhythm emulation; there is no benign-but-bursty control).

Leakage is the headline caveat. paperC found the original “100 % family accuracy” was an artifact: coverage_ratio is a per-family constant (0.133 steady / 0.200 phasic) and cv_workingset/f1_phase are family-conditional. Our iv=500 data reproduces it exactly — coverage_ratio alone scores 1.000. So every number below is reported two ways: the leaky FULL feature set vs. the leakage-free AGNOSTIC set (7 features: apf_mean/std, cepstral peak + SNR, stationarity, n_pairs, n_windows); and under two protocols: LORO (leave-one-replicate-out, optimistic — a workload appears in train and test) vs. LOWO (leave-one-workload-out, the honest generalization-to-an-unseen-workload test).

On our delete-as-you-go dataset (0/66 starved) the same leakage-free test rises to 0.636, above baseline, and the phasic cepstral SNR — the rhythm signature — is now a median 8.4 dB on 29/30 cells with ≥8 windows (v3 computed it on too few DOF). Relieving DOF starvation turned a non-generalizing signal into a (modestly) generalizing one.

The leave-one-workload-out number above (binary 0.788) can still lean on same-family siblings: hold out seq, and the other three ransomware remain in training to teach “ransomware shape.” To isolate general threat-shape from same-family memorization we hold out an entire family and classify it from the others.

What this says for the thesis

  1. APF is a coarse behavioral fingerprint, and the generalization it supports depends on what is held out. Seen-before: near perfect (5-class 1.0, 11-way 0.89). Unseen workload with same-family siblings in training: binary 0.79.   2. For novel families, prefer anomaly detection over supervised classification. Leave-one-family-out: the supervised classifier misses 3/4 of a held-out threat family, while one-class anomaly (trained only on benign) flags novel threats at ROC-AUC 0.93. Rule: known families → classify; novel/unseen family → anomaly.
  3. The Plan 05 capture fix paid off downstream. The honest, leakage-free family signal went from below-baseline (starved v3) to above-baseline (this dataset) — a direct, measured benefit of relieving DOF starvation.
  4. Leakage discipline is mandatory. coverage_ratio alone reproduces “perfect” accuracy; only AGNOSTIC + held-out (LOWO/LOFO) numbers are trustworthy.
  5. Not a detector (as stated). The no-benign-bursty-control gap and the cross-family failure mean this is behavioral characterization, not a security-detection claim — consistent with the thesis's stance.

Summary: what we got, what it means, what we contribute

The whole arc in plain language — the result, its meaning, the conclusions, and what is actually new.

1. What we were testing

The signal (APF). Every ~half-second we snapshot the VM's memory and compute one number: the fraction of 4 KB pages that changed since the last snapshot — the active page fraction. It is a single scalar over time. The question: how much can you tell about what a machine is doing from this one coarse number?

The dataset. 66 captures = 11 workloads × 3 durations × 2 repeats. Two groups: 5 threat-like (4 ransomware variants + a filesystem scanner) and 6 benign (5 memory microbenchmarks + a hashtable app).

2. What we got

The capture itself (Plan 05's job). The old v3 captures were degrees-of-freedom starved (53/132 cells with ≤3 analysis windows). Our pipeline produced 0 of 66 starved cells, 29,003 snapshot pairs, all validated. The capture problem is solved.

What APF can identify — three granularities, two regimes (seen-before vs. never-seen), all leakage-controlled, best feature set:

TaskSeen-beforeNovel workloadNovel whole family
11-way “which exact program”0.89n/an/a
5-class “which behavior family”1.000.36 (chance)n/a
binary threat/benign1.000.790.30–0.64 (threats mostly missed)
anomaly (flag the abnormal)—0.930.93

Chance baselines: 11-way 0.09, 5-class 0.36, binary 0.55.

Three findings that shaped those numbers:

  • Leakage (a trap we avoided). A naive run gives “100 %” — but one feature (coverage_ratio) is a per-family constant that leaks the label. Stripped out, the honest numbers are those above.
  • The capture fix measurably helped the science. On the starved v3 data the honest family signal was 0.466 (below chance); on our clean data it is 0.636 (above chance, significant). Better capture → a real downstream gain.
  • Simple shape features help, with a surprise. Adding peak/variance features lifted novel-workload threat/benign 0.64→0.79 and anomaly 0.74→0.93 — recovering the I/O-bound batched threat but not the low-and-slow slowburn, the opposite of the prediction. Measuring beat guessing.

3. What it means

  • APF is a coarse behavioral fingerprint — reliable at bursty-vs-steady and at identifying behavior it has seen before (family 1.0, exact program 0.89), but it cannot pin fine identity on something genuinely new.
  • “Generalization” was partly memorization until stress-tested. The 0.79 on a novel workload leaned on same-family siblings in training. Remove a whole family and supervised threat detection collapses (held out all ransomware → missed 3 of 4; recall 0.25): high-activity encryptors look like high-activity benign workloads when nothing ransomware-shaped trains the boundary.
  • Anomaly detection behaves differently — better for novelty. It learns only “normal” and flags deviation, so it never needed to see the threat family: 0.93 on a novel family where the supervised classifier fails.
  • Two workloads are irreducibly confusable in memory: the stealth threat slowburn and the benign pagefault are both near-idle with rare spikes. What separates them is disk I/O, which APF structurally cannot see.

4. What we conclude

  1. Capture quality is a first-class variable. Relieving DOF starvation moved the downstream family signal from below-chance to above-chance — the engineering enabled the science.
  2. APF supports behavioral characterization, not security detection. Strong on known behavior, weak on novel identity, and honest about it.
  3. Use the right tool for the regime: known families → supervised classification (near-perfect); novel/unseen threat family → anomaly detection (0.93).
  4. Methodology matters as much as results: without leakage control and held-out-family testing you get a fake 100 %. The honest numbers are lower but real.
  5. The single scalar has a known blind spot (low-and-slow / I/O-bound threats) that a second, non-memory signal (disk-I/O rate) would close — a concrete next step.

5. Contributions

Engineering / infrastructure

  • A capture pipeline that eliminates DOF starvation end-to-end (delete-as-you-go, sustain-loop, Rust queue consumer, real-disk workload scratch, cold-boot SSH hardening) — 66/66 clean, validated against C1–C8.
  • A reproducible, fully offline downstream harness (trajectory→cells adapter, leakage-aware classifiers, anomaly detectors, family/workload stress tests) — one command reproduces every number.

Scientific findings

  • Evidence that capture fidelity changes the conclusion: the same leakage-free analysis flips from non-generalizing (starved v3) to generalizing (our data) — a result about why prior weak findings were weak.
  • A clean characterization ladder of exactly what a single memory scalar supports (near-perfect known, coarse-only novel workload, failing novel family) with the controls that make the numbers trustworthy.
  • The supervised-vs-anomaly regime distinction for novelty, with the failure mode (cross-family supervised collapse) quantified.
  • A small leakage-free feature contribution (peak/variance) with a measured lift and an honest negative (recovers batched, not slowburn) that points precisely at the one missing signal (disk I/O).
  • A normal-behavior profiler built offline from the benign cells: a per-behavior fingerprint catalog, an interpretable normal-envelope detector (ROC-AUC 0.95), and a masquerade map pinning which normal behavior each threat impersonates — normal behavior characterized as a deliverable, not just an anomaly backdrop.
  • Honest-science practice: reproducing and controlling a known leakage, testing at the hardest held-out-family level, and correcting our own wrong prediction in writing.
What we are not claiming. Not a deployable malware detector; synthetic threats; small sample (11 workloads, 2 reps); no benign-but-bursty control. Stated, not hidden — which is what makes the positive claims defensible.
